# Деплой imbored на Vercel + домен imbored.cc

Гайд написан под текущее состояние проекта (Next.js 16, App Router, `node:sqlite`).
Разделено на **что делаешь ты** (аккаунты, клики) и **что делаю я** (код).

---

## 0. База данных: миграция на Turso — ✅ сделано

Раньше база была файлом `data/imbored.db` через встроенный `node:sqlite`. На Vercel это не работает:
файловая система serverless-функций эфемерная, а запросы приходят в разные инстансы — библиотека
пользователя исчезала бы между запросами.

**Проект переведён на Turso** (облачный SQLite):

- `lib/db.ts` полностью переписан на асинхронный клиент `@libsql/client`;
- заодно убраны N+1 запросы — `getStaleAppids`, `getGamesMeta` и доска комнат теперь ходят в базу
  один раз вместо цикла;
- `getDb()` возвращает промис с кэшем на процесс: миграции схемы выполняются один раз за холодный старт;
  на уже доведённой базе это четыре обращения к Turso, потому что ALTER и пересборки закрыты версией
  схемы (`schema_v` в `catalog_meta`). Добавляешь колонку — подними `CURRENT_SCHEMA_V` в `lib/db.ts`,
  иначе живая база её не получит;
- **локально Turso не нужен** — если `TURSO_DATABASE_URL` не задан, используется файл `data/imbored.db`,
  так что дев-режим и демо работают без единого ключа.

Проверено: 101 тест зелёный, продакшен-сборка чистая, база создаётся с нуля, все сценарии
(подбор, комната с матчем, совместимость, портрет) прогнаны на живом сервере.

## 4. Vercel (делаешь ты, 10 минут)

1. [vercel.com](https://vercel.com) → **Sign up with GitHub** (дай доступ к репозиторию `imbored`).
2. **Add New → Project** → выбери `imbored` → **Import**.
3. Framework Vercel определит сам (Next.js). Build-команды **не трогай**.
4. Разверни **Environment Variables** и добавь. Все переменные — для Production,
   Preview и Development, **кроме `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`: эти
   только для Production**. У превью своя база, см. «Превью: своя база» ниже.

| Переменная | Значение | Обязательна |
|---|---|---|
| `TURSO_DATABASE_URL` | `libsql://...` из шага 3 | да |
| `TURSO_AUTH_TOKEN` | токен из шага 3 | да |
| `SESSION_SECRET` | длинная случайная строка (32+ символа) | **да, критично** |
| `APP_BASE_URL` | `https://imbored.cc` | да |
| `STEAM_API_KEY` | ключ из steamcommunity.com/dev/apikey | да (иначе только демо) |
| `ANTHROPIC_API_KEY` | ключ с platform.claude.com | нет (без него — эвристика) |
| `CRON_SECRET` | длинная случайная строка | **да, иначе патчноуты не обновляются** |
| `STEAM_STORE_CC` | `us` или `ru` — регион цен | нет |
| `LLM_MODEL` | переопределение модели, по умолчанию `claude-haiku-4-5` | нет |
| `NEXT_PUBLIC_DONATE_URL` | ссылка на Boosty / Ko-fi | нет |

> **Про срок входа.** Кука живёт год и продлевается при каждом заходе (роут
> `/api/session/touch`), так что переавторизовываться через Steam не нужно, пока
> заходишь хотя бы раз в год. Сессии лежат в таблице `sessions` и гасятся
> кнопками на `/library` — по одному устройству или сразу по всем. Смена
> `SESSION_SECRET` тоже разлогинивает, но всех и сразу, так что для обычного
> выхода она не нужна.

> **`SESSION_SECRET` — не пропускай.** Им подписывается кука сессии. Сейчас в коде есть
> дев-заглушка; если оставить её в проде, куку можно будет подделать и зайти под чужим SteamID.
> Сгенерировать: любой менеджер паролей, длина 32+, или попроси меня — выдам строку.

5. **Deploy**. Через ~2 минуты получишь адрес вида `imbored-xxxx.vercel.app` — уже рабочий.

### Регион функций

По умолчанию Vercel исполняет функции в Вашингтоне (`iad1`), а база Turso живёт
в Европе. Тогда каждый запрос к базе пересекает Атлантику туда и обратно, а на
странице их несколько подряд, и на холодном старте тоже. Поэтому регион задан в
`vercel.json`: `"regions": ["dub1"]`, Дублин, рядом с `aws-eu-west-1`, где стоит
база. На Hobby регион функций один, больше и не нужно.

Проверить после деплоя:

```bash
curl -sI https://imbored.cc/whatsnew | grep -i x-vercel-id
```

Ответ вида `x-vercel-id: fra1::dub1::…`. Первый регион — точка входа, ближайшая к
тому, кто спрашивает, и она может быть любой. Второй — где исполнилась функция,
и там должен быть `dub1`. `/whatsnew` взят потому, что он всегда рендерится
заново. У ответа из кэша CDN второго региона нет вовсе, функция не звалась.

Если база в другом регионе (он виден в хосте `TURSO_DATABASE_URL`: Vercel →
Settings → Environment Variables), поменяй регион в `vercel.json`, а не в
дашборде, чтобы он проходил через ревью. Пары: `aws-eu-west-1` → `dub1`,
`aws-eu-central-1` → `fra1`, `aws-us-east-1` → `iad1`.

### Превью: своя база, не продовая

Каждый пуш ветки создаёт превью-деплой, а его сборка и первый холодный старт
прогоняют миграции схемы (`migrateDb` в `lib/db.ts`). С продовыми `TURSO_*`
изменения схемы из ветки попадают на живую базу ещё до ревью, а тестеры превью
пишут в продовые таблицы строки, которых код `main` не знает. Откат ветки
ни то, ни другое не вернёт. Поэтому:

1. Vercel → Settings → Environment Variables: у `TURSO_DATABASE_URL` и
   `TURSO_AUTH_TOKEN` оставь только область **Production**.
2. Создай базу для превью копией прода и токен к ней:

   ```bash
   turso db create imbored-preview --from-db imbored
   turso db tokens create imbored-preview
   ```

3. Добавь `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` превью-базы с областью
   **Preview**, и там же `PREVIEW_OWN_DB=1`.
4. **Redeploy** последнего превью.

Не оставляй превью совсем без базы: без `TURSO_DATABASE_URL` на Vercel `getDb`
падает с внятной ошибкой, и превью не откроется. Поэтому шаги 1 и 3 делаются
вместе.

`PREVIEW_OWN_DB=1` снимает страховку в коде. Без флага превью не выполняет
разрушающие миграции (пересборку таблиц, починку JSON-колонок игр), не
записывает версию схемы и флаги этих шагов, чтобы прод после мержа довёл их
сам, и пишет в Runtime Logs строку с `"event":"migrate-skipped"`. Починка JSON
пропускается молча: чтобы узнать, есть ли что чинить, нужен тот же полный скан.
Страховка нужна на случай, если переменные снова разъедутся, поэтому флаг
ставь только туда, где база действительно своя.

## 5. Домен imbored.cc (делаешь ты, 10 минут + ожидание DNS)

4. Подожди 5–30 минут. Vercel сам выпустит HTTPS-сертификат и покажет зелёную галочку.

## 6.5. Каталог игр: наполнение (делаешь ты, один раз)

Приложение работает и без этого шага, но блок «Нет в твоей библиотеке» будет
пустым: рекомендовать новое не из чего, пока каталог не наполнен.

Каталог собирается **локально**, а не в облаке. Так задумано: отладка прямо по
Turso сожгла бы квоту записей, а локальный SQLite пишет мгновенно.

```bash
npm run seed:catalog
```

Обходит магазин Steam и складывает карту территории — около 170 тысяч игр
с тегами, датами выхода, отзывами и ценами. Занимает 15–40 минут. Прогон
**возобновляемый**: если прервётся, тот же запуск продолжит с места обрыва.
Начать заново — `npm run seed:catalog -- --restart`.

```bash
npm run catalog:promote -- --limit=3000
```

Отбирает самые обсуждаемые игры, догружает теги с весами и арт, спрашивает
свежие отзывы у совместных игр и раскладывает по рабочим таблицам, применяя
фильтры актуальности. Можно запускать повторно — очередь двигается дальше.

```bash
npm run catalog:report -- --name=counter
```

Показывает, **какие решения принял фильтр**: сколько игр отсеяно и почему,
какие версии признаны устаревшими. Вытеснение версий стоит просматривать
глазами — ошибка здесь заметнее пользователю, чем лишняя игра в выдаче.

```bash
npm run news:sync -- --limit=200
```

Собирает патчноуты: обходит RSS-ленты игр, отделяет обновления от анонсов и
распродаж, просит Claude пересказать крупные в одну-две фразы. Наполняет
вкладку «Что нового» и блок патчей на странице игры.

Дальше это делает крон сам (`vercel.json` → `/api/cron/news`), но **первый
массовый обход дешевле прогнать здесь**: у функции на Vercel потолок 60 секунд
на вызов, а тут ограничений нет. Темп — 1.7 секунды на игру, тот же лимитер
хоста, что у отзывов, так что 200 игр это примерно 6 минут.

Прогон возобновляемый: очередь и её курсоры живут в таблице `news_poll`,
повторный запуск продолжает с места обрыва. Посмотреть, кого опросит, не
трогая сеть — `npm run news:sync -- --dry-run`.

**Заливка в облако.** Скрипты пишут в Turso, если задана переменная окружения:

```bash
TURSO_DATABASE_URL=... TURSO_AUTH_TOKEN=... npm run catalog:promote -- --limit=3000
```

Порядок: сначала собери и проверь каталог локально, потом залей в облако.
Наоборот — дорого и медленно.

**Битые JSON-колонки игр.** У части игр `tags_json` оказался закодирован
дважды: в колонке JSON-строка, а в ней объект (так лежала Dota 2). Приложение
такое уже читает, но в базе строки стоит починить — и она чинится сама, один
раз: миграция `repair_tags_v1` в `migrateDb` при первом старте прода после
деплоя этой правки. Она переписывает исходные данные, поэтому перед деплоем:

```bash
# сколько строк затронет (только чтение); CASE — потому что json_type
# на битом JSON бросает, а не отвечает
turso db shell imbored "SELECT COUNT(*) FROM games WHERE CASE WHEN json_valid(tags_json) THEN json_type(tags_json) != 'object' ELSE 1 END"
# бэкап таблицы игр
turso db shell imbored ".dump games" > games-backup.sql
```

После деплоя в Runtime Logs будет строка `"event":"migrate-repaired"` с числом
починенных строк (если было что чинить), а тот же `SELECT COUNT(*)` вернёт 0.

Локальный `data/catalog.db` починит та же миграция при первом запуске любого
скрипта наполнения. `catalog:publish` миграцию по нему не гоняет и не повезёт
каталог в облако, пока там есть битые строки: откажется ещё до подключения и
назовёт команду починки:

```bash
npm run catalog:repair-tags -- --dry-run   # что починится
npm run catalog:repair-tags                # починить data/catalog.db
```

**Патчноуты после деплоя.** Крон закрыт секретом, поэтому `CRON_SECRET` должен
быть в переменных Vercel — без него роут отдаёт 401 и лента перестаёт
пополняться. На тарифе Hobby Vercel зовёт крон примерно раз в сутки независимо
от расписания в `vercel.json`, поэтому пропускная способность набирается
цепочкой вызовов: срез отвечает сразу, работает в фоне и сам зовёт следующее
звено. На Pro можно сгустить расписание до `0 */3 * * *` и поднять
`maxDuration` до 300 — код при этом не меняется.

Проверить руками:

```bash
curl -H "x-cron-secret: $CRON_SECRET" https://imbored.cc/api/cron/news
```

**Живы ли кроны.** Код ответа выше — это 202 до всякой работы, упавший срез
по нему не виден. Каждое звено пишет отметку о себе в `catalog_meta`
(`news_last_slice`, `digest_last_slice`, `pages_last_slice`), и её читает
`/api/cron/health`: 200 — все живы, 503 — какой-то крон молчит дольше порога
(новости и пересказы — 3 часа, карточки — 26), упал или оборвал цепочку; в
ответе видно, какой и почему. Крон на паузе (`*_paused = 1`) проверку не
валит, но помечен `paused`. Этот же адрес дёргает часовой воркфлоу
`.github/workflows/cron.yml`, так что поломка приходит письмом от GitHub.

```bash
curl -H "x-cron-secret: $CRON_SECRET" https://imbored.cc/api/cron/health
```

У карточек расписание одно, суточное, поэтому их подстраховывает крон
новостей: закончив свою цепочку, он пинает `/api/cron/pages`, если отметка
карточек старше 26 часов или последняя запись — обрыв передачи звена.
Отказ передачи звена или пинка пишется в Runtime Logs одной строкой JSON с
`"event":"cron-chain-break"`.

**Свежесть каталога.** Отзывы и онлайн игр пула сверяет тот же крон карточек,
рядом со срезом: каждое звено берёт до двухсот игр, давно не сверенных
(колонка `reviews_at`), спрашивает отзывы одним запросом GetItems и онлайн у
совместных игр, и пишет узкими UPDATE — `updated_at`, `alive` и вердикт
курации не трогает. Круг по пулу — около недели. Колонка `reviews_at` и её
индекс появляются сами при первом холодном старте после деплоя (`ALTER TABLE
… ADD COLUMN`, данные не переписываются). Итог звена — поле `сигналы` в
`pages_last_slice` (`checked`, `reviews`, `ccu`, `stopped`), сводка — раздел K
в `npm run news:report`. Пауза общая с карточками: `pages_paused = 1`.
`catalog:publish` сверенные кроном отзывы, свежие цены и онлайн не
откатывает: замер едет, только если он не старше облачного.

Новинки в пул так не попадают — это по-прежнему `seed:catalog` →
`catalog:promote` → `catalog:publish` руками. Еженедельный GitHub Action для
этой цепочки не заведён: ему нужны `TURSO_*` в секретах репозитория и
`data/catalog.db` артефактом — решение за тобой.

**Семантика игр (без модели).** Оси сложности, освоения и темпа, длина
захода и время до веселья (`lib/semantics.ts`) лежат в своей таблице
`game_semantics`, а не в колонках `games`, — `catalog:publish` её не трогает.
Таблица появляется сама при первом холодном старте после деплоя (`CREATE
TABLE IF NOT EXISTS`, существующие данные не переписываются). Дальше её
наполняет крон карточек: каждая карточка получает семантику из того же ответа
appreviews, что и вердикт отзывов, — без лишних запросов к Steam и без модели
(поле `withSemantics` в `pages_last_slice`). Первого круга по каталогу можно
не ждать:

```bash
npm run semantics:build                                # приор по тегам в data/catalog.db: секунды, без сети
npm run semantics:report                               # покрытие, распределения, сверка с разметкой
# проверь черновую разметку scripts/semantics-golden.json: поправь метки, поставь checked: true
npm run semantics:build -- --with-reviews --limit=500  # + отзывы Steam, ≈15 мин на порцию; повторять
npm run semantics:build -- --publish                   # сколько поедет; к облаку не подключается
npm run semantics:build -- --publish --yes             # залить в Turso (TURSO_* из .env.turso)
npm run semantics:report -- --remote                   # тот же отчёт по облаку, только чтение
```

`semantics:build` пишет только в локальный `data/catalog.db`, даже если
`TURSO_*` заданы, — облако только через `--publish --yes`. Заливка не
откатывает прод: приор по тегам не затирает посчитанного кроном по отзывам,
старая запись не переписывает свежую, новая версия формата вытесняет старую.
`--with-reviews` помнит, за чьими отзывами уже ходил (`reviews_at`), и
следующая порция начинается с новых игр; после трёх отказов Steam подряд
останавливается сам. `semantics:report` выходит с кодом 1, если согласие с
разметкой ниже 70%: тогда семантику в скоринг пускать рано — править таблицу
`TAG_PRIOR` в `lib/semantics.ts` или разметку, а не порог.

**Соседи игр (без модели).** Двенадцать похожих на каждую игру по всему
вектору тегов с весом редкости (`lib/neighbors.ts`) лежат в своей таблице
`game_neighbors`; `catalog:publish` её не трогает, таблица появляется сама
при первом холодном старте после деплоя. Пока она пуста, полка «Похожие» на
карточке и «Как «X», но…» на `/play` работают по-старому — по одному тегу
полки. Наполнить:

```bash
npm run neighbors:build                         # посчитать в data/catalog.db: секунды, без сети
npm run neighbors:build -- --show=1145360       # соседи одной игры глазами (здесь Hades)
npm run neighbors:build -- --publish            # сколько поедет; к облаку не подключается
npm run neighbors:build -- --publish --yes      # залить в Turso (TURSO_* из .env.turso)
```

Перед первой заливкой сверь в Turso Dashboard → Usage остаток квоты записи:
первый раз едет около 70 тысяч строк (двенадцать на игру). Повторная заливка
на том же каталоге пишет только изменившиеся строки и называет их число.
Пересобирать — после каждого `catalog:publish` с новыми играми или тегами:
иначе у новинок соседей нет, и их полка остаётся по тегу. Облачные строки
игр, которых нет в локальном каталоге, заливка не трогает.

**Русские имена тегов.** Словарь тегов (`tags`) хранит рядом с английским
именем русское — `name_ru`, из того же списка Steam, склеенного по `tagid`.
Колонка появляется сама при первом холодном старте после деплоя (`ALTER TABLE
… ADD COLUMN`, схема v3, данные не переписываются). Английское имя остаётся
ключом всех таблиц подбора; русское — только подпись. Заполнить:
`catalog:promote` докачивает русский словарь, если в локальном его ещё нет, а
`catalog:publish` везёт `name_ru` в облако и пустым уже привезённое не
затирает.

Интерфейс базу ради подписей не читает: они лежат статической картой в
`lib/tagsru.steam.ts`, и выводятся через `tagRu` (`lib/tagsru.ts`). Карту
генерирует скрипт — раз в несколько месяцев, когда Steam заводит новые теги
(тег без перевода просто остаётся английским):

```bash
npm run tags:ru                            # оба словаря из Steam, два GET без ключа
npm run tags:ru -- --db=data/catalog.db    # то же из tags.name_ru локального каталога
```

Кривой перевод Steam правится в `lib/tagsru.overrides.ts` — генератор этот
файл не трогает.

**Трейлеры и кадры.** Микротрейлер Steam (несколько секунд геймплея без звука,
mp4 и webm) и его постер лежат в колонке `games.trailer_json` (`lib/trailer.ts`).
Колонка появляется сама при первом холодном старте после деплоя (`ALTER TABLE
… ADD COLUMN`, схема v4, данные не переписываются). Берутся из того же
GetItems двумя флагами, `include_trailers` и `include_screenshots`, но не в
прогреве библиотеки: с ними ответ втрое тяжелее (1,7 МБ против 0,55 МБ на
двести игр). Их просят `catalog:promote` (новые игры приходят в пул сразу с
трейлером), крон карточек — одним GetItems на срез из двадцати карточек (поле
`withTrailers` в `pages_last_slice`; его отказ срез не останавливает), и
отдельная доливка для уже залитого пула — без неё крон доберётся до верха
каталога только к следующему кругу, через полгода:

```bash
npm run catalog:media -- --dry            # сколько игр пула без трейлера или кадров
npm run catalog:media -- --limit=6000     # долить: ≈30 запросов GetItems, пара минут
npm run catalog:publish                   # довезти trailer_json и кадры в облако
```

Доливка пишет две колонки узким UPDATE и `updated_at` (lastmod карты сайта)
не трогает. Пустое ничего не затирает — ни у доливки, ни у апсерта, ни у
`catalog:publish`: трейлер и кадры, привезённые в облако, заливка каталога без
них не сотрёт. Игры без трейлера в Steam (Half-Life, часть старых) остаются
без него и попадут в следующий прогон. С `TURSO_DATABASE_URL` доливка пишет
прямо в облако, как и остальные скрипты наполнения, — но по правилу выше
сначала локально, потом `catalog:publish`.

На сайте трейлер — раздел «В движении» на `/game/…` и строка-кнопка в герое
`/play`. Ролик (2–3 МБ, 6–8 секунд) качается только по нажатию, постер — лениво;
после деплоя проверь на `/game/730`, что кнопка играет ролик, а в Runtime Logs
нет `csp-report` с `media-src`.

**Снимок выдачи в фидбеке и отчёт по нему.** К каждой оценке на `/play`
прикладывается снимок выдачи (`lib/feedbackctx.ts`): где стояла карточка
(герой, выбранная из «Ещё вариантов», полка покупок), каким движком собрана
выдача, подталкивание, источник кандидата и части скора. Лежит в колонке
`feedback.ctx_json`; она появляется сама при первом холодном старте после
деплоя (`ALTER TABLE … ADD COLUMN`, схема v5, данные не переписываются). На
экран снимок не выводится; через 90 дней суточная уборка (`sweepStale`, крон
новостей) его стирает, оценка остаётся — так и сказано в /privacy, разделы 01
и 06. Отчёт читает только строки со снимком и ничего не пишет:

```bash
npm run feedback:report                   # по локальной data/imbored.db
npm run feedback:report -- --remote       # по облаку (TURSO_* из .env.turso), только чтение
npm run feedback:report -- --remote --days=14 --with-demo
```

Доля ниже тридцати оценок в строке помечена «мало данных» — выводы по ней
делать рано. Демо-личности по умолчанию не считаются.

**Исход совета.** Запуск с `/play` или `/daily` и переход в магазин за не
купленной пишут строку в таблицу `outcomes` (`lib/outcome.ts`) с минутами до —
по последнему снапшоту. Каждый новый снапшот библиотеки в течение двух недель
дописывает минуты после и то, появилась ли игра в библиотеке (покупка); сверка
идёт на любой дороге, что приносит снапшот, — прогрев, вход через Steam,
подключение по ссылке. Если в игру сыграно от 15 минут, `/play` и `/daily` раз
в сутки спрашивают «как тебе?» (`/api/outcome`); «Зацепило» пишется и в оценки.
Таблица появляется сама при первом холодном старте (`CREATE TABLE IF NOT
EXISTS`), строки старше 90 дней стирает суточная уборка, `user:forget` удаляет
их вместе со всем остальным. Второй раздел `feedback:report` — сколько после
совета на самом деле сыграли, по источникам и слотам.

## 6.6. Удаление данных по запросу (делаешь ты, по письму)

/privacy, раздел 06, обещает удалить всё по письму на hello@imbored.cc за 30
дней. Удаление — одна команда, учётки Turso берутся из `.env.turso`:

```bash
npm run user:forget -- https://steamcommunity.com/profiles/7656119XXXXXXXXXX
```

Без `--apply` скрипт только считает строки по таблицам и ничего не трогает.
Если счёт похож на правду — та же команда с `--apply`: всё удаляется одной
пачкой (профиль и портрет, снимки и годовые отметки библиотеки, оценки и
баны, исходы советов, сессии, игра дня, голоса и участие в комнатах,
комнаты этого человека целиком, его ключи лимитера). Ссылка вида `/id/<имя>`
разворачивается через Steam API и требует `STEAM_API_KEY` в окружении; без
него попроси SteamID64.

Запускать из задеплоенного кода: скрипт намеренно не гоняет миграции, и если
в базе ещё нет таблицы из списка, пачка откатится целиком, ничего не удалив.
Картинки портрета в кэше Vercel доживают до часа, превью в мессенджерах
отозвать нельзя — это сказано в /privacy, раздел 05.

## 6.7. Заголовки безопасности и CSP (делаешь ты, неделю по разу в день)

Все заголовки задаёт `next.config.ts`, а собирает `lib/csp.ts`: `nosniff`,
`X-Frame-Options: DENY` (сайт нельзя встроить во фрейм), `Referrer-Policy`,
`Permissions-Policy` без камеры, микрофона и геолокации. `x-powered-by` больше
не отдаётся. Проверить после деплоя:

```bash
curl -sI https://imbored.cc/ | grep -i -E 'content-security|x-frame|x-content-type|x-powered-by'
```

Политика содержимого пока стоит как `Content-Security-Policy-Report-Only`: она
ничего не блокирует, только сообщает, что заблокировала бы. Каждое нарушение
браузер шлёт на `/api/csp-report`, а тот пишет в Runtime Logs одну строку JSON с
`"event":"csp-report"` (одинаковые схлопываются, так что строк немного).

Неделю смотри Vercel → Logs по `csp-report`, или консоль браузера на `/`, `/play`,
`/game/730` и `/whatsnew`:

- `blocked` со схемой `chrome-extension`, `moz-extension`, `safari-web-extension`
  — это расширения посетителей, их не чиним;
- любой другой хост — пропуск в политике. Хост картинок Steam добавляется в
  `STEAM_IMG_DOMAINS` в `lib/steamhtml.ts`, остальное — в `cspDirectives` в
  `lib/csp.ts`;
- `media-src` — это трейлеры на `/game/…` и в герое `/play` (кнопка «В
  движении»): ролик идёт с `video.akamai.steamstatic.com`, и политика пускает
  любой `*.steamstatic.com`. Нарушение с другим хостом Steam для видео значит,
  что Valve переехала на новый CDN, — поправь `VIDEO_BASE` в `lib/trailer.ts`
  и директиву рядом.

Если за неделю ничего, кроме расширений, не пришло, запрет включается отдельным
коммитом: `CSP_ENFORCE = true` в `lib/csp.ts` и соседний тест в
`lib/csp.test.ts`, который нарочно держит `false`. После деплоя пройди чек-лист
из раздела 7: пропущенный хост в режиме запрета молча пропадает у всех.

Хэша и nonce у скриптов нет, и это не упущение: почему — в шапке `lib/csp.ts`.

## 6.9. Превью ссылок и поиск (делаешь ты, один раз после деплоя)

Каждая страница объявляет свой `og:url` и `canonical` (раньше все наследовали
`og:url` главной). `/portrait/`, `/compat/` и `/room/` больше не закрыты в
`robots.txt`: закрытыми они не показывали поисковику свой `noindex`, а X не
разворачивал их карточки. Из поиска их теперь убирает заголовок
`X-Robots-Tag: noindex` — правила в `lib/robots.ts`. Проверить (только GET и
HEAD):

```bash
curl -s https://imbored.cc/robots.txt                                   # нет Disallow: /portrait/ и /compat/ без $
curl -s https://imbored.cc/privacy | grep -o '<meta property="og:url"[^>]*>'   # .../privacy, не корень
curl -s https://imbored.cc/ | grep -o '<link rel="canonical"[^>]*>'     # https://imbored.cc
curl -sI https://imbored.cc/portrait/<твой steamid> | grep -i x-robots-tag     # noindex
curl -sI "https://imbored.cc/portrait/<твой steamid>/card.png" | grep -i x-robots-tag   # noindex
```

Что сделать руками:

- **Google Search Console → Индексирование → Страницы.** Если там есть адреса
  `/portrait/…`, `/compat/…` или `/room/…` со статусом «Проиндексировано,
  несмотря на блокировку в robots.txt», — теперь краулер увидит `noindex` и
  уберёт их сам при следующем обходе. Быстрее — «Удаления» → временно скрыть
  префикс `https://imbored.cc/portrait/`.
- **Яндекс Вебмастер → Индексирование → Страницы в поиске** — то же самое.
- **Кэш превью.** VK и Facebook помнят старый `og:url` главной. Если ссылки на
  `/privacy`, `/whatsnew` или `/support` уже где-то разворачивались, обнови их
  карточки: Facebook — Sharing Debugger → «Scrape Again», VK — метод
  `pages.clearCache` из VK API (он сбрасывает кэш превью внешней ссылки).
- **X.** Вставь ссылку на свой портрет в окно нового поста (публиковать не
  нужно): карточка с картинкой должна развернуться.

## 6.10. Логи ошибок: что искать (делаешь ты, когда что-то не так)

Отдельного хранилища ошибок нет — всё в Vercel → Logs, одной строкой JSON на
событие. Ищи по полю `event`:

- `"event":"server-error"` — исключение долетело до Next (`instrumentation.ts`).
  `digest` — тот же код, что человек видит на экране ошибки: жалоба «показало
  код a1b2c3» ищется по `a1b2c3`. `path` и `referer` — под масками
  (`/compat/:steamid`, `/room/:id`), строки запроса нет.
- `"event":"swallowed"` — сбой, который код поймал сам и отдал человеку фолбэк
  (`logSwallowed` в `lib/errlog.ts`). Поле `where` — место, `status` — ответ
  чужого сервиса, `code` — код ошибки сети или базы, `repeats` — сколько таких
  же промолчали с прошлой строки (одно место пишет не чаще раза в минуту).
- `"event":"client-error"` — падение в браузере (`instrumentation-client.ts` и
  границы ошибок шлют отчёт на `/api/clienterr`). `code` — тот же код, что на
  экране «Что-то сломалось»: у клиентских он начинается с `c` (`c1wdipwl`), у
  серверных это `digest` из цифр. `kind`: `boundary` — страницу поймала
  граница ошибок, `error` и `rejection` — упало вне React (клик, таймер,
  промис). Одна и та же поломка у разных людей даёт один код, а одинаковые
  строки прорежены — так что строк мало даже при массовом сбое после деплоя.

Как читать `where`:

| `where` | что значит |
| --- | --- |
| `auth/return:steam`, `connect:steam` | Steam Web API не отдал библиотеку. `status: 403` — ключ отозван или неверен (Steam → Web API Key), `429`/`5xx` — лимит или обслуживание (по вторникам) |
| `auth/return:openid` | steamcommunity.com не ответил на проверку входа — человек видит «Steam сейчас не отвечает» |
| `auth/return:db`, `connect:db` | Steam ответил, а база не приняла запись. `code: BLOCKED` или ошибки квоты — Turso → Usage |
| `ratelimit:check`, `sessions:lookup` | база недоступна, и лимиты с отзывом сессий работают вслепую (fail-open). Разовая строка — моргание, строки подряд с `repeats` — чинить |
| `catalog:ensure-meta`, `deals:refresh` | прогрев или цены не получили ответ Steam; `status: 429` — нас ограничивают |
| `pagejob:*`, `news:feed` | кроны карточек и новостей; `pagejob:pros-cons` — модель недоступна (баланс, ключ) |

- [ ] Главная открывается, коллаж артов едет

- [ ] Переключатель темы работает и запоминается

- [ ] После наполнения каталога: в подборе есть секция «Нет в твоей библиотеке»
- [ ] В пятничном режиме «с друзьями» предлагается CS2, а не CS 1.6
